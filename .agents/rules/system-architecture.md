# System Architecture Rules

1. **Monorepo Boundaries**: Keep `apps/web` (Next.js frontend), `apps/api` (Node.js/Fastify or Express API server), `apps/workers` (BullMQ workers: orchestrator, media, rendering, publishing), `packages/shared` (Zod schemas, TypeScript types, constants), `packages/database` (Prisma schema, client, migrations), `packages/ai-providers` (LLM, Vision, STT, TTS, Embeddings abstraction), `packages/remotion-engine` (Composition JSON compiler, reusable Remotion components, templates), and `packages/integrations` (Postiz adapter, S3/MinIO storage, MCP adapters) strictly separated.
2. **No Frontend Heavy Execution**: Never run Remotion rendering, FFmpeg transcoding, Whisper transcription, or direct LLM orchestration inside Next.js API routes or browser clients. The frontend communicates exclusively with `apps/api` via REST and SSE/WebSockets.
3. **Database as Source of Truth**: Persist every workflow stage transition (`PENDING` -> `ANALYZING` -> `PLANNING` -> `SCRIPTING` -> `COMPOSING` -> `RENDERING` -> `REVIEWING` -> `REVISING` -> `AWAITING_APPROVAL` -> `APPROVED` -> `SCHEDULED` -> `PUBLISHED`, plus `FAILED` / `CANCELLED`) in PostgreSQL before enqueuing the next BullMQ job. Never rely on in-memory state.
4. **Structured Composition AST**: AI agents must generate and mutate validated JSON Composition AST specifications (`CompositionSpecSchema`), never arbitrary untrusted React code files. The Remotion compiler deterministically renders the validated JSON AST into Remotion components.
5. **Human Approval Gate**: No workflow may transition from `AWAITING_APPROVAL` to `SCHEDULED` or `PUBLISHED` without an explicit persisted user approval record (`ApprovedByUserId` + timestamp) or an explicitly enabled workspace automation policy.
